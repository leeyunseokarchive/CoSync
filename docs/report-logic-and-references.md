# CoSync 리포트 산출 로직 및 근거 자료

이 문서는 CoSync 갭 리포트(`app/gap-report/page.tsx`)가 화면에 보여주는 숫자(정합도 %, 갭 등급, 카테고리별 막대)가 **정확히 어떤 코드에서 어떻게 계산되는지**, 그리고 리포트 문구에 인용된 통계·법 조항이 **어디까지 실제로 확인 가능한지**를 정리한다. 알고리즘 서술은 `lib/gap.ts` 코드를 그대로 옮긴 것이며, 통계/법률 항목은 웹 리서치로 원출처를 재확인한 결과다.

## 1. 개요 — 무엇을 산출하는가

CoSync 온보딩 진단은 팀원 각자에게 20개 문항(기본 12 + 심화 8)을 답하게 한 뒤, 두 가지를 산출한다.

1. **문항별 팀 상태(카테고리형)** — `getIssueStatus` / `getTeamIssueStatus`. 히트맵 셀 색상(`match`/`diff`/`conflict`/`unanswered`)에 쓰인다.
2. **정합도 점수(수치형)** — `pairGap` → `computeGapSummary`. 게이지에 표시되는 `overallAlignment`(%)와 카테고리별 막대, 그리고 `LOW/MID/HIGH/CRITICAL` 등급을 만든다.

두 계산은 같은 `toxicPairs`(치명적 조합) 테이블을 공유하지만 서로 독립적인 함수이며, 목적이 다르다: 전자는 "이 셀을 무슨 색으로 칠할까"이고, 후자는 "팀 전체 정합도가 몇 점인가"이다. 이 문서는 후자(수치 계산)를 정확히 재현 가능하도록 공식과 상수를 코드 그대로 옮기고, 전자는 참고로만 다룬다.

산출된 값은 `app/gap-report/page.tsx`의 `teamInsight`에서 게이지 값(`alignmentScore`), 등급 뱃지(안정/점검/주의/위험), 카테고리별 진단 막대, 그리고 우선순위 대화 주제 정렬(`CAT_WEIGHT_BY_ID` 기준)에 그대로 쓰인다.

## 2. 진단 문항 구조 (20문항 · 카테고리 · 가중치)

`lib/gap.ts`의 `QUESTION_CONFIGS`, `CAT_LABELS`, `CAT_WEIGHTS`를 그대로 옮긴다.

```ts
export const CAT_LABELS = ["역할 & 책임", "이탈 & 회수", "비전 & 가치관", "조달 & 운용", "의사결정 & 실행", "지분 & 보상"];

// 정규화 가중치 (출처: 국내 스타트업 팀 와해 및 분쟁 원인 실증 분석 MVP V3) — lib/gap.ts 주석 원문
const CAT_WEIGHTS = [0.11, 0.11, 0.11, 0.17, 0.22, 0.28];
```

가중치 합은 `0.11×3 + 0.17 + 0.22 + 0.28 = 1.00`으로, 6개 카테고리 모두 응답되었을 때 정규화 분모가 1이 되도록 설계돼 있다(3장 참조).

| cat idx | 카테고리 (`CAT_LABELS`) | 가중치 (`CAT_WEIGHTS`) | 문항 수 | 문항 필드 (`QUESTION_CONFIGS`의 `field`) | 진단 구분 |
|---|---|---|---|---|---|
| 0 | 역할 & 책임 | 0.11 | 3 | `extraWorkPriority`, `extraWorkPrinciple`, `underperformanceAction` | 기본(Q1–Q3) |
| 1 | 이탈 & 회수 | 0.11 | 3 | `exitRecoveryPriority`, `exitCleanupTiming`, `exitDisputeResolution` | 기본(Q4–Q6) |
| 2 | 비전 & 가치관 | 0.11 | 3 | `exitVision`, `pivotCriteria`, `dealbreaker` | 기본(Q7–Q9) |
| 3 | 조달 & 운용 | 0.17 | 3 | `fundingRunway`, `spendingApproval`, `investmentCriteria` | 기본(Q10–Q12) |
| 4 | 의사결정 & 실행 | 0.22 | 4 | `decisionStructure`, `decisionFailure`, `actionVsConsensus`, `deadlockTolerance` | 심화(Q13–Q16) |
| 5 | 지분 & 보상 | 0.28 | 4 | `salaryStructure`, `equityStructure`, `profitDistribution`, `growthStrategy` | 심화(Q17–Q20) |

각 문항 설정(`QuestionConfig`)은 `field`(응답 키), `toxicPairs`(치명적 충돌로 간주되는 옵션 조합 목록), `cat`(소속 카테고리 인덱스)로 구성된다. 예:

```ts
{ field: "extraWorkPriority", toxicPairs: [["3","4"]], cat: 0 },
{ field: "equityStructure", toxicPairs: [["2","4"]], cat: 5 },
```

기본 진단(Q1–Q12) 12문항을 전원이 완료해야 리포트가 열리며(`isTeamComplete`, `BASIC_FIELDS` 기준), 심화 진단(Q13–Q20)은 선택 사항으로 완료 시에만 심화 히트맵과 해당 카테고리 점수가 노출된다(`showAdvancedHeatmap`, `allHaveAdvancedData`).

## 3. 갭/정합도 산출 공식 (코드 기준)

### 3.1 문항 하나, 두 사람 답변의 갭 — `pairGap`

```ts
const pairGap = (v1: string, v2: string, toxicPairs: [string, string][]): number => {
  const s1 = v1[0];
  const s2 = v2[0];
  if (s1 === s2) return 0;
  for (const [p1, p2] of toxicPairs) {
    if ((s1 === p1 && s2 === p2) || (s1 === p2 && s2 === p1)) return 3;
  }
  const d1 = parseInt(s1);
  const d2 = parseInt(s2);
  return isNaN(d1) || isNaN(d2) ? 1 : Math.abs(d1 - d2);
};
```

- 두 답변의 **선택지 번호(응답 문자열의 첫 글자)** 를 비교한다.
- 같으면 `0`(일치).
- 그 문항에 등록된 `toxicPairs`(치명적 조합, 순서 무관)에 해당하면 `3`(최댓값, 치명적 충돌).
- 그 외에는 `|옵션번호 차이|`(예: 옵션 "1"과 "3"이면 갭 2). 옵션이 숫자로 파싱되지 않으면 안전값 `1`을 반환.

옵션이 1~4번으로 구성돼 있으므로 `pairGap`의 최댓값은 3(옵션 1과 4 사이 또는 toxicPair)이다.

### 3.2 문항 갭 — 전체 멤버 쌍 중 최악(max)

```ts
for (const q of QUESTION_CONFIGS) {
  let worstGap = 0;
  let answeredByPair = false;
  for (let i = 0; i < members.length; i++) {
    for (let j = i + 1; j < members.length; j++) {
      const v1 = members[i][q.field];
      const v2 = members[j][q.field];
      if (!v1 || !v2) continue;
      answeredByPair = true;
      const g = pairGap(v1, v2, q.toxicPairs);
      if (g > worstGap) worstGap = g;
    }
  }
  if (!answeredByPair) continue; // 2명 이상이 답한 문항만 집계
  ...
}
```

한 문항의 갭은 **팀원 전체 쌍 조합 중 가장 나쁜(max) `pairGap`** 값이다. 2인 팀이면 쌍이 1개뿐이라 그 값 그대로, 3인 이상이면 모든 쌍을 비교해 최악값을 취한다. 두 사람 다 응답하지 않은 쌍은 건너뛰고, 그 문항에 응답한 쌍이 하나도 없으면(`answeredByPair === false`) 해당 문항은 이번 집계에서 통째로 제외된다(카운트되지 않음).

### 3.3 카테고리 갭 `G_i` — 응답된 문항의 평균

```ts
const catGaps = catGapSums.map((sum, k) =>
  catCounts[k] > 0 ? sum / catCounts[k] : 0
);
```

카테고리 `k`의 갭 `G_k`는 그 카테고리에서 **집계된(응답 쌍이 있었던) 문항들의 `worstGap` 평균**이다(0~3 범위). 응답이 하나도 없는 카테고리는 `G_k = 0`으로 처리되지만, 아래 정규화 단계에서 가중치 자체가 분모·분자에서 제외되므로 점수에 유리하게 왜곡되지 않는다.

### 3.4 원점수 `rawScore` — 가중합

```ts
// S_total = Σ W'_i × G_i (max = 3, since Σ W'_i = 1 and max G_i = 3)
const rawScore = catGaps.reduce((acc, g, k) => acc + CAT_WEIGHTS[k] * g, 0);
```

`rawScore = Σ CAT_WEIGHTS[k] × G_k`. 6개 카테고리 모두 응답되고 전부 최악(G_k=3)이면 `rawScore`의 이론적 최댓값은 `Σ CAT_WEIGHTS[k] × 3 = 3`(가중치 합이 1이므로).

### 3.5 정합도 `overallAlignment` — 정규화 및 반올림

```ts
// 미진단 카테고리를 제외하고, 실제 답변된 카테고리 가중치 합으로 정규화
const answeredWeight = catCounts.reduce((sum, count, k) =>
  count > 0 ? sum + CAT_WEIGHTS[k] : sum, 0);
const overallAlignment = answeredWeight > 0
  ? Math.round((1 - rawScore / (answeredWeight * 3)) * 100)
  : 100;
```

`overallAlignment = round( (1 − rawScore / (answeredWeight × 3)) × 100 )`

- `answeredWeight`는 **응답된 문항이 하나라도 있는 카테고리**의 `CAT_WEIGHTS` 합이다(진단하지 않은 카테고리는 분모에서 제외 — "미진단 카테고리를 가중치 정규화에서 제외"). 예: 심화 진단을 아무도 안 했다면 `answeredWeight = 0.11×3 + 0.17 = 0.44`가 되고, 6개 다 있으면 `1.00`.
- `rawScore`의 이론적 상한이 `answeredWeight × 3`이므로(3.4 참조, 단 미진단 카테고리는 `G_k=0`이라 자연히 상한 계산에서도 기여 없음), 이 비율은 0~1 사이가 되어 `%`로 자연스럽게 변환된다.
- `answeredWeight === 0`(아무 카테고리도 응답 안 됨)이면 `overallAlignment = 100`으로 기본값 처리.
- 2인 미만(`members.length <= 1`)이면 `computeGapSummary`는 즉시 `overallAlignment: 100, gapScore: "LOW"`인 빈 결과를 반환한다.

카테고리별 표시값도 동일한 정규화를 개별 적용한다:

```ts
const alignment = Math.round((1 - catGaps[k] / 3) * 100);
```

(카테고리 단위는 항상 `G_k / 3`으로 나누므로 팀 전체 정규화와 달리 가중치 보정이 없다 — 카테고리 자체의 심각도만 본다.)

### 3.6 갭 카운트 `gapCount`

```ts
if (worstGap > 0) gapCount++;
```

응답된 문항 중 `worstGap > 0`(즉 완전 일치가 아닌) 문항 개수를 전체 문항 기준으로 누적한 값. 카테고리와 무관하게 팀 전체의 "차이 나는 문항 수"를 나타낸다.

## 4. 갭 등급(LOW~CRITICAL) 및 해석

```ts
const toGapScore = (alignment: number): GapScore => {
  if (alignment >= 85) return "LOW";
  if (alignment >= 65) return "MID";
  if (alignment >= 45) return "HIGH";
  return "CRITICAL";
};
```

| 등급 | 정합도 구간 | UI 표기 (`app/gap-report/page.tsx`) | 해석 |
|---|---|---|---|
| `LOW` | ≥ 85 | 안정 단계 | 핵심 기준이 대체로 맞춰져 있음. 문서화만 하면 충분. |
| `MID` | 65 ~ 84 | 점검 단계 | 지금은 큰 문제 없지만 성장 속도가 빨라지면 간극이 실행력을 잠식할 수 있음. |
| `HIGH` | 45 ~ 64 | 주의 단계 | 지금 정리하지 않으면 중요한 결정마다 충돌로 번질 가능성이 높음. |
| `CRITICAL` | < 45 | 위험 단계 | 인식 차이가 실행 단계에서 경영권 분쟁으로 전환될 수 있는 수준. |

이 등급은 `overallAlignment`(팀 전체)와 각 카테고리 `alignment`(카테고리 개별) 양쪽에 동일한 함수로 적용된다. 팀 전체 등급이 `teamInsight.gapScore`로 게이지 아래 뱃지에, 카테고리별 등급이 `cat.gapScore`로 카테고리 막대 옆 라벨(안정/점검/주의/위험)에 쓰인다. 카테고리가 미진단(`alignment === null`)이면 등급 없이 "미진단"으로 표시된다.

## 5. 근거 통계 및 법률 리서치 (출처 포함)

`app/gap-report/page.tsx`의 `SCRIPTS` 객체(`stat`/`stake` 필드, 문항 Q1~Q20 각각)에 이미 인용돼 있는 통계·법 조항을 1차 출처로 삼아 웹 리서치로 원출처를 재확인했다. 확인 가능한 항목은 원출처를 명시하고, 확인 불가한 항목은 "출처 미확인"으로 표기했다(삭제하지 않음 — 신뢰도 관리 목적).

### 5.2 관련 법 조항 (이탈·정산 관련, 주주간 계약의 법적 성격)

## 6. 한계 및 향후 고도화 (LLM 기반 근거 제시형 확장)

- **현재 구조의 한계:** `SCRIPTS`의 `stat` 문구는 정적 텍스트로 하드코딩돼 있어, 원출처가 바뀌거나(예: 다음 연도 창업기업 실태조사 갱신) 통계가 갱신돼도 자동으로 반영되지 않는다. 또한 5장에서 확인했듯 일부 수치(민법 조문 번호 등)는 검증 없이 삽입되면 오류가 누적될 위험이 있다.
- **RAG 기반 근거 연결:** `docs/AI_기반_공동창업팀_운영_합의_진단_및_합의안_생성_플랫폼CoSync_보고서.md`에서 제안하는 "근거 제시형 합의 진단 엔진" 방향과 연결하면, `SCRIPTS`의 정적 통계 텍스트 대신 검색-근거제시(RAG) 파이프라인으로 문단 단위 출처 링크를 실시간으로 붙이고, 자동 사실 검증 로직으로 "출처 미확인" 항목을 주기적으로 재검증하는 구조가 다음 단계로 적합하다.
- **법률 조문 자동 검증:** 국가법령정보센터 Open API 등을 연동해 조문 번호·조문 내용을 정기적으로 대조하면, 이번에 발견한 "제718조 → 제719조" 같은 오류를 코드 배포 전에 자동으로 잡아낼 수 있다.
- **통계 신뢰도 뱃지:** 리포트 UI 자체에 "확인됨 / 출처 미확인" 신뢰도 표시를 추가해, 사용자가 어떤 근거가 검증된 것인지 스스로 판단할 수 있게 하는 것도 고려할 만하다.
