## 1. 목적과 범위

CoSync 서비스 플로우는 `각자 답변 → 팀원 답변과의 갭 비교 → 합의 → 계약서 생성`이다. 이 문서는 그중 **첫 단계인 "각자 답변" 화면의 질문 템플릿**을 정의한다.

조항마다 답변해야 할 값의 성격이 다르다. 금액, 기간, 비율, 사람 지정, 멤버별 배분, 사실 기재가 모두 섞여 있다. 하나의 입력 폼으로는 커버되지 않으므로 **7종 입력 템플릿**을 정의하고, 15개 질문을 각 템플릿에 매핑한다.

**범위에 포함**: 질문 위저드 목업 1개 페이지, 입력 템플릿 7종, 질문 15개.
**범위에서 제외**: 갭 비교 화면, 합의 화면, 계약서 생성. Firestore 연동. (모두 별도 작업)

## 2. 확정된 전제

브레인스토밍에서 사용자가 확정한 사항이다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 회사 설립 시점 | **설립 전 기준** | 3조·3의2조·3의3조가 "설립 전 계약" 전용 조문. 설립 전 기준이므로 역할·지분 질문 포함 |
| 답변 단위 | **성격별 분기** | 금액·기간·비율·선택형은 각자 답변 후 합의. 회사명·신원 같은 사실정보는 입력만 하고 합의 대상 아님 |
| 팀원 답변 노출 | **블라인드 + 진행률만** | 앵커링 방지. 상단에 "3명 중 2명 응답"만 표시. 기존 온보딩 진단과 동일 |
| 화면 구조 | **위저드 1문항 1화면** | 이전/다음 버튼으로 전환 |
| 위약벌(8조) | **기준금액 1 + 비율 1 → 4개 빈칸 자동 파생** | 빈칸 6개를 개별로 물으면 부담 과다 |
| 추가 후보 질문 | **포함하되 `제안` 배지 표시** | 개발 과정에서 확정 문항과 구분 가능해야 함 |

## 3. 입력 템플릿 7종

각 템플릿은 하나의 React 컴포넌트다. 질문 데이터가 `type` 필드로 템플릿을 지정하고, 위저드가 그에 맞는 컴포넌트를 렌더한다.

### 3-1. `amount` — 금액

프리셋 칩 3~4개 + 직접입력. 입력값을 한글 금액으로 병기해 자릿수 오입력을 막는다(`100000000` → `일억 원`).

```
┌────────────────────────────────────────┐
│ [ 5천만 원 ] [ 1억 원 ]● [ 3억 원 ] [직접입력]│
│                                        │
│   ₩ [    100,000,000    ]              │
│      일억 원                            │
└────────────────────────────────────────┘
```

- 숫자 입력은 `inputMode="numeric"`, 3자리 콤마 자동 삽입, tabular figures
- 사용처: Q4(의사결정 금액 기준), Q14(위약벌 기준금액)

### 3-2. `duration` — 기간

단위 칩(일/개월/년)과 값 스테퍼. 베이스 계약서에 이미 값이 있는 조문은 `기본값` 배지로 표시하고 그 값을 초기값으로 넣는다.

```
┌────────────────────────────────────────┐
│ [ 1년 ] [ 3년 ]● [ 5년 ] [ 직접입력 ]      │
│                                        │
│   [ − ]   3   [ + ]  년                 │
│           ⓘ 베이스 계약서 기본값: 5년      │
└────────────────────────────────────────┘
```

- 사용처: Q5(데드락 협의 기간), Q8(경업금지), Q9(계속근무), Q10(베스팅/클리프), Q12(처분 제한)

### 3-3. `percent` — 비율

슬라이더 + 숫자 입력. 슬라이더 눈금에 숫자만 두지 않고 **의미 라벨**을 붙인다(예: `50% 과반` / `67% 특별결의` / `75%`). 비율 하나가 무슨 뜻인지 창업자가 알기 어렵기 때문이다.

```
┌────────────────────────────────────────┐
│   [ 67 ] %                             │
│   ├────────────●─────────────┤          │
│   50%        67%           100%        │
│   과반      특별결의          전원         │
└────────────────────────────────────────┘
```

- 사용처: Q13(드래그얼롱 발동 지분율), Q14(위약벌 비율)

### 3-4. `choice` — 단일 선택 카드

옵션 카드 그리드. 각 카드는 라벨 + 1줄 설명. `variant: "person"`이면 팀원 아바타 + 이름 + 역할로 렌더한다(별도 템플릿을 만들지 않고 variant로 처리).

- 사용처: Q5(데드락 최종 결정권자, `person`), Q3(주식 종류), Q11(퇴사 시 매수 가격), Q15(관할법원)

### 3-5. `matrix` — 멤버별 행 입력

팀원 수만큼 행이 생기고 각 행에 입력한다. 두 가지 변형:

- `variant: "text"` — 역할 서술. 추천 칩(CEO/CTO/개발/영업/재무/디자인) 클릭으로 채우고 자유 편집 가능
- `variant: "allocation"` — 지분율. **합계 100% 실시간 검증**. 합계가 100이 아니면 하단에 잔여/초과 표시하고 다음 버튼 비활성화

```
┌─────────────────────────────────────────────┐
│ 김민준 (나)   [CEO] [CTO] [개발]              │
│              [ 제품 총괄 및 투자 유치      ]   │
│ 이서연        [ 백엔드 개발 및 인프라 운영  ]   │
│ 박도윤        [ 디자인 및 프론트엔드       ]   │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ 김민준 (나)     [ 50 ] %   ████████████       │
│ 이서연          [ 30 ] %   ███████            │
│ 박도윤          [ 20 ] %   █████              │
│ ─────────────────────────────────────────    │
│ 합계 100%  ✓                                 │
└─────────────────────────────────────────────┘
```

- 사용처: Q6(역할·업무분담, `text`), Q7(지분율, `allocation`)

### 3-6. `fields` — 사실정보 폼

라벨-값 쌍 나열. 합의 대상이 아니므로 미리보기는 있지만 갭 비교 대상이 아님을 화면에 명시한다.

- 사용처: Q1(회사명·체결일·부수), Q2(당사자 신원)

### 3-7. `composite` — 조합

위 템플릿 2개를 한 화면에 세로로 배치하고, 두 값에서 파생되는 결과를 하단에 자동 표시한다.

- Q5 = `duration`(협의 기간) + `choice/person`(최종 결정권자)
- Q10 = `choice`(적용 여부) + `duration` × 2(베스팅 기간 / 클리프 기간). 적용 안 함을 고르면 하위 입력을 숨긴다
- Q14 = `amount`(기준금액) + `percent`(비율) → 8조 ①②③⑤ 4개 빈칸 자동 채움

## 4. 질문 15개 — 조문 순서

계약서 조문 순서대로 배치한다. 미리보기가 계약서 흐름과 같은 순서로 나타나 사용자가 문서를 조립하는 감각을 갖는다.

`✓` = 확정 문항(사용자 지정 8개) · `제안` = 추가 후보(배지 표시)

| # | 배지 | 질문 | 조문 | 템플릿 | 참고 정보 |
|---|---|---|---|---|---|
| 1 | 제안 | 회사명·체결일·계약서 부수 | 전문·말미 | `fields` | 합의 대상 아님 |
| 2 | 제안 | 당사자 신원 (이름·주민등록번호·주소) | 전문·서명란 | `fields` | 본인 것만 입력 |
| 3 | 제안 | 주식의 종류 | 전문·3의3조 | `choice` | 보통주식 / 종류주식 |
| 4 | ✓ | 얼마를 넘는 투자부터 전원 합의가 필요한가 | 2조①7호 | `amount` | 베이스 1억 원 |
| 5 | ✓ | 합의가 안 되면 며칠 협의하고, 누가 결정하는가 | 2조③ 신설 | `composite` | 변호사 예시: 7일 + 대표자 |
| 6 | ✓ | 각자 무엇을 맡는가 | 3의2조 | `matrix/text` | — |
| 7 | ✓ | 지분을 어떻게 나누는가 | 전문·3의3조 | `matrix/allocation` | 합계 100% |
| 8 | 제안 | 퇴사 후 몇 년간 경업을 금지하는가 | 4조② | `duration` | 베이스 1년 |
| 9 | ✓ | 최소 몇 년 근무 의무를 지는가 | 5조① | `duration` | **정합성 경고 대상** |
| 10 | 제안 | 베스팅·클리프를 적용하는가 | 5조 강화 | `composite` | 예: 4년 베스팅 / 1년 클리프 |
| 11 | 제안 | 퇴사 시 주식을 얼마에 되사는가 | 5조②·9조③ | `choice` | 베이스는 일괄 액면가. 변호사는 귀책 차등 권고 |
| 12 | ✓ | 몇 년간 주식을 팔 수 없는가 | 6조 | `duration` | 베이스 5년, 통상 5~10년 |
| 13 | ✓ | 몇 % 이상이면 전원 강제 매각인가 | 7의2조① | `percent` | 낮으면 소수주주 강제, 높으면 엑싯 봉쇄 |
| 14 | ✓ | 계약을 어기면 얼마를 무는가 | 8조 | `composite` | 통상 1억 (1천만~10억 분포) |
| 15 | 제안 | 분쟁 시 어느 법원인가 | 16조② | `choice` | 베이스 서울중앙지방법원 |

### 4-1. 조문 간 정합성 경고 (Q9)

베이스 5조②는 "3년 이내에 퇴사하는 경우" 액면가 매수권을 규정한다. 5조①의 계속근무 의무 기간을 3년 미만으로 입력하면 두 항이 어긋난다.

- 트리거: Q9 입력값 < 3년
- 표시: 입력 필드 아래 경고(에러 아님) — "5조②는 3년 기준으로 작성되어 있습니다. 3년 미만으로 정하면 두 항의 기준이 달라집니다."
- 차단하지 않음. 사용자가 의도적으로 다르게 정할 수 있다.

유일한 조건부 로직이다. 나머지 14개 문항은 입력과 표시만 한다.

### 5-1. 계약서 반영 미리보기

이 목업의 핵심 차별점이다. 입력값이 **실제 조문 원문 안에 하이라이트되어** 즉시 나타난다. 사용자는 자기 답이 계약서 어디로 가는지 그 자리에서 본다.

- 조문 원문은 「최종 계약서 샘플.md」에서 그대로 가져온다
- 입력 전에는 원문의 `[  ]` 자리가 점선 플레이스홀더로 표시된다
- 입력 후에는 그 자리가 indigo 배경 + bold로 치환된다
- Q14는 입력 2개에서 파생된 4개 조항이 모두 나타난다

### 5-2. 참고 정보 (아코디언, 기본 접힘)

`progressive-disclosure` 원칙. 펼치면 3가지가 나온다.

1. 변호사 조언 / 통상 범위
2. 이 값이 낮을 때의 리스크
3. 이 값이 높을 때의 리스크

Q13(드래그얼롱)처럼 양방향 리스크가 뚜렷한 문항에서 특히 중요하다.

### 5-3. 사이드바 그룹 (5개)

`app/mockup/questions/page.tsx`의 `qm-sidebar`를 그대로 쓴다. 한글 + 영문 서브라벨 구조 동일.

| 그룹 | 영문 | 문항 |
|---|---|---|
| 계약 기본 | Contract Basics | 1, 2, 3 |
| 의사결정 | Decision & Deadlock | 4, 5 |
| 역할·지분 | Roles & Equity | 6, 7 |
| 근무·이탈 | Tenure & Exit | 8, 9, 10, 11 |
| 처분·제재 | Transfer & Penalty | 12, 13, 14, 15 |

각 그룹에 완료 개수(`2/3`)를 표시하고, 현재 그룹은 좌측 indigo 바로 강조한다.

### 5-4. `제안` 배지

확정 문항이 아닌 7개 문항에 표시한다. 개발 중 구분이 목적이므로 눈에 띄되 방해하지 않아야 한다.

- 위치: eyebrow 행의 조문 태그 오른쪽
- 스타일: amber 계열 점선 테두리 pill, 텍스트 `제안`
- 사이드바 항목에도 동일 색 점 하나를 붙여 목록에서도 식별 가능
- 색만으로 구분하지 않는다 (`color-not-only`) — 텍스트 `제안`을 항상 포함

## 6. 데이터 구조

질문은 배열 하나로 선언한다. 위저드는 이 배열을 순회할 뿐이므로 문항 추가·삭제·순서 변경이 배열 편집으로 끝난다.

```ts
type QuestionTemplate =
  | { type: "amount"; presets: number[]; defaultValue?: number }
  | { type: "duration"; unit: "일" | "개월" | "년"; presets: number[]; baseValue?: number }
  | { type: "percent"; marks: { value: number; label: string }[] }
  | { type: "choice"; variant?: "person"; options: { id: string; label: string; desc: string }[] }
  | { type: "matrix"; variant: "text" | "allocation"; chips?: string[] }
  | { type: "fields"; fields: { key: string; label: string; placeholder: string }[] }
  | { type: "composite"; parts: QuestionTemplate[] };

type ContractQuestion = {
  id: string;
  group: string;            // 사이드바 그룹
  article: string;          // "제2조 ③"
  articleTag: string;       // "DEADLOCK"
  proposed: boolean;        // true면 `제안` 배지
  consensus: boolean;       // false면 합의 대상 아님(사실정보)
  title: string;            // 질문 문장
  desc: string;             // 왜 정해야 하는지
  template: QuestionTemplate;
  preview: string;          // 조문 원문. 치환 자리는 {0} {1}
  reference?: { advice?: string; lowRisk?: string; highRisk?: string };
};
```

`preview`의 `{0}`, `{1}`이 입력값으로 치환되는 자리다. Q14처럼 파생값이 여러 조항에 들어가는 경우 `preview`를 배열로 둔다.

## 7. 파일 구성

```
lib/contractQuestions.ts              — 질문 15개 데이터 + 타입
app/mockup/contract-questions/page.tsx — 위저드 셸 (사이드바·헤더·푸터·상태)
  └ components/ContractQuestionInputs.tsx — 템플릿 7종 렌더러
```

3개 파일로 끝낸다. 템플릿당 파일을 나누면 7개 파일이 각각 30줄짜리가 되어 오히려 읽기 어렵다. 렌더러 파일이 300줄을 넘어가면 그때 나눈다.

상태는 `useState<Record<string, unknown>>` 하나. 목업이므로 Firestore도 localStorage도 쓰지 않는다.

## 11. 검증

목업이지만 두 곳에 실제 로직이 있으므로 확인 수단을 남긴다.

1. **지분율 합계 검증** — 합이 100이 아니면 다음 버튼 비활성 + 잔여량 표시
2. **Q9 정합성 경고** — 3년 미만 입력 시 경고 노출, 차단은 안 함

두 함수를 순수 함수로 분리하고 `lib/contractQuestions.test.ts`에 assert 기반 자체 점검을 둔다. 프레임워크 없이 기존 `lib/annexClauses.test.ts` 관례를 따른다.

나머지는 렌더링과 상태 전환뿐이므로 별도 테스트를 두지 않는다.
